# 时序违例处理


> 记录 FPGA 合成器工程从"210 违例可用"恶化到"1804 违例不可用"、再一路修回"284 违例"的全过程。
> 重点是**诊断方法**和**通用原则**，不是某次改动的流水账。

---

## 一、为什么突然要研究这个

**10-16 那版**：210 个建立时间违例、最差 slack −0.613 ns，上板验证过声音正常（音色/力度/音量都对）。
**当时以为只是"差 3%，运气好"，没当回事。**

**10-18 加了 CC71-74（通道级实时调滤波器）之后**：违例暴涨到 **1804**、最差 slack **−10.955 ns**。

> ⚠ **一处重要澄清（避免误导后人）**：同一轮上板时"所有音色都炸"（啸叫 + 咔哒），
> **但那不是时序违例造成的**。真正的根因是 `chan_table` 的四个调制字段（CC71~74）复位成 0，
> 被换算成 `q_coeff = 0`（阻尼为零 → 滤波器自激）和 `attack/release_step = 1`（瞬间包络 → 咔哒）。
> 修法是把这四个字段的复位值改成 **64（中心 = 不调制）**，改完仿真验证通过才算确认。
> **时序违例和"炸"是同时出现的两件事，不是因果关系** —— 这个判断搞反了会白费很多时间。
>
> 判断依据：**上电的测试模式声音正常，一弹音就炸**。测试模式走 `test_voice_gen`、
> 不经过 `SFV`/ADSR；正常模式才经过。所以问题只在声部层，与时序无关。

**但违例本身必须处理**：1804 个违例、最差 −10.955 ns 的位流，功能随时可能出错；
而且 P&R 要 90 分钟、反复迭代根本做不下去。

## 二、怎么看时序报告

### 2.1 文件位置

```
impl/pnr/full_system.tr          主报告（文本，800KB~1MB）
impl/pnr/full_system.timing_paths 最差路径的逐节点延迟（Gowin GUI 二次导出）
impl/pnr/full_system.rpt.txt      资源占用
```

**注意：`.tr` 是 P&R 完成后才生成的。综合阶段不做时序分析** ——
综合报告（`gwsynthesis/full_system_syn.rpt.html`）里没有可用的时序估计。

### 2.2 三个关键数字

**① `Numbers of Setup Violated Endpoints`** —— 违例端点数（不是路径数）

```
10-16 : 210
10-18 (CC71-74 之后) : 1804
10-18 (SVF 流水之后) : 851
10-18 (dump 两拍之后) : 284
```

**② `2.3 Max Frequency Summary`** —— **这个比违例数更能说明问题**

```
NO.  Clock Name              Constraint    Actual Fmax   Level
1    clk50                   50.000 MHz    186.087 MHz   7      ← 裕量巨大
2    clk12288                24.576 MHz    379.138 MHz   4      ← 裕量巨大
3    PLL CLKOUT0             49.152 MHz     45.843 MHz   13     ← **这个不够**
```

**所有违例都在 PLL 输出的 49.152 MHz 时钟域上。`clk50` 和 `clk12288` 的裕量都很大。**

**③ `Slack` / `Data Arrival Time` / `Data Required Time` / `From` / `To`**

```
Slack             : -1.468
Data Arrival Time : 30.488
Data Required Time: 29.020
From              : u_sched/u_sq/cyc_5_s1
To                : u_sched/u_vf/pf_phase_inc_37_s0
```

**`From` / `To` 两行是最有价值的信息** —— 直接告诉你是哪条逻辑链。

### 2.3 一个重要的坑：报告的路径数 ≠ 违例端点数

`Numbers of Setup Violated Endpoints` 报告 851，但 `.tr` 里只列出 **25 条**最差路径的详情。
**其余 826 个端点看不到。**

**怎么判断"是一个锥还是散落各处"**：看那 25 条的 `From`/`To` 是否集中。

```
全部 From 都是 cyc_5_s1，To 分散在 u_vf / u_fx / u_parse
  → 不是"25 条独立路径"，而是"一个控制信号扇出到 25 个地方"
  → 修那一个信号就能全解决
```

**这个判断非常关键** —— 决定了"改一处"还是"改几百处"。

## 三、核心认识：**P&R 时间由"距离时序收敛的差距"决定**

### 3.1 数据

| 轮次 | 违例 | 最差 slack | PLL 实际 Fmax | P&R 耗时 |
|---|---|---|---|---|
| 10-16（CC71-74 之前） | 210 | −0.613 ns | **未记录** | 约 35 分钟 |
| 10-18（加 CC71-74） | 1804 | −10.955 ns | 42.771 MHz | 约 90 分钟 |
| 10-18（SVF 流水） | 851 | −3.036 ns | 42.771 MHz | 82 分钟 |
| 10-18（dump 两拍） | 284 | −1.468 ns | 45.843 MHz | **33 分钟** |

### 3.2 结论

**布线器的 Routing Phase 2/3 是"时序修复"阶段，离收敛越远它越拼命尝试，耗时越长，而且往往修不好。**

```
离收敛 3%   → 35 分钟
离收敛 15%  → 82~90 分钟（而且白费）
```

**注意 1655 违例和 851 违例的耗时几乎一样（90 vs 82）** —— 说明**不是"违例数"决定耗时，
而是"差得有多远"决定**。

### 3.3 实用推论：可以预测 P&R 时长

**信号 ①：布局耗时**（`full_system.p` 的时间戳 − `cmd.do` 的时间戳）

```
≤12 分钟  → 总耗时 30 分钟左右
≥20 分钟  → 总耗时 80 分钟左右
```

**信号 ②：日志出现 `[70%] Routing Phase 1 completed` 的时刻**

```
总耗时 ≈ 2 ~ 3 × 该时刻已耗时
```

**两条实测数据**：27 分钟 → 82 分钟（×3.0）；16 分钟 → 33 分钟（×2.1）。

**操作建议：启动 P&R 后 15 分钟看一次日志，用这个公式估算，决定值不值得等。**

## 四、四个案例

### 案例 ①：常量变成运行时值 → 常量折叠消失（最容易忽略）

**症状**：加了 CC74（实时调截止频率）之后，违例从 210 暴涨到 1804。

**原因**：

```verilog
// 改前：f_coeff 是编译期常量 30000
.f_coeff(def_f_coeff)      // 综合器做常量折叠，SVF 里的乘法被大幅优化

// 改后：f_coeff 来自通道表的运行值
.f_coeff(f_coeff_r)        // 折叠不了，SVF 的真实延迟暴露
```

**SVF 的真实延迟是 33.69 ns，而周期只有 20.345 ns。**

**教训**：**"把一个常量换成寄存器"不是零成本改动。** 综合器对常量的优化幅度常常远超预期。
**改之前应该先问：这个值被优化掉了吗？**

### 案例 ②：单周期内的双重乘法 → 分级流水（SVF）

**问题代码**（Chamberlin 状态变量滤波器的差分方程）：

```verilog
low  = low  + f × band
high = input − low − q × band      // 用更新后的 low
band = band + f × high             // 用更新后的 high
```

**串行路径**：`f×band`（64 位乘）→ 加 → 饱和 → 减 → 饱和 → `f×high`（第二次 64 位乘）→ 加 → 饱和
**= 33.69 ns。两次乘法串联。**

**关键认识：SVF 每个样本只更新一次（48 kHz），而时钟是它的 1024 倍。有 1024 拍可用，拆 4 级只占 4 拍。**

**修法**：把运算拆到 4 个时钟里，每级之间插寄存器。

```verilog
第 1 级：f×band、q×band（并行）
第 2 级：low_n = sat(low + f·band)
第 3 级：high_n = sat(in − low_n − q·band)
第 4 级：f×high、band_n、写回、选输出
```

**⚠ 关键原则：只插寄存器，不改变运算顺序和舍入。**

**为什么不能用"数学化简"**：`band_n` 可以展开成 `band + f·in − f·low − f(f+q)·band`，
数学等价、只有 1 次乘法深，**但舍入路径完全不同** ——
`tb_svf_voice` 是**逐样本位精确比对**，化简后必然失败。而且滤波器的听感会变。

**流水化后 `tb_svf_voice` 位精确通过（0 处失配）** ✓

**连带改动**：`voice_mono` 的使能链要跟着顺延（`vca_en`/`adsr_en` 从 `rdy_d2` → `rdy_d4`），
测试台的采样点也要顺延。

### 案例 ③：组合链太长 → 拆成两拍（chan_table 的 dump）

**问题**：`chan_table` 在"把 FIFO 条目写进后备 bank"时，一拍内完成：

```
FIFO 读出 → d_old 16通道 mux → 弯音乘法 → 查表(64选1) → 插值乘法 → 加法 → 写回
```

**耗时分解**（从 `.timing_paths` 读出来的）：

```
FIFO 读出          0.65 ns
d_old 16通道mux    2.78 ns
预处理             1.81 ns
mult_1775 乘法     3.01 ns
之后（查表+插值）  13.7 ns     ← 大头
────────────────────────
总计 32.0 ns（要求 28.98）
```

**修法**：拆两拍

```
第 1 拍：FIFO读 → mux → 乘法 → 算 bidx       ≈ 8 ns，锁存 d_old/d_fld/d_val/d_ch/bidx/dsemi
第 2 拍：查表 → 插值乘法 → 加法 → 写回       ≈ 14.7 ns
```

**做法**：把 `apply_field` 函数拆成"前半段（第 1 拍组合算）+ 后半段（第 2 拍用锁存值）"，
函数多加两个输入 `p_bidx` / `p_dsemi`，弯音分支不再自己算乘法和索引。

**dump 周期从 16 拍变 32 拍，占 1024 拍的 3%，完全够。**

**效果**：851 → 284 违例，P&R 82 → 33 分钟。

### 案例 ④：控制信号组合解码 + 巨大扇出（voice_slot_seq）

**问题**：

```verilog
always @(*) begin
    slot_vld = 1'b0;
    slot     = 0;
    for (k = 0; k < G; k = k + 1)
        if (cyc == (1 + k*STRIDE)) begin    // 11 位计数器的 4 路比较器
            slot_vld = 1'b1;
            slot     = k;
        end
end
```

**`slot_vld` 是 `cyc` 的组合解码，然后扇出到全系统**：
`voice_mono × 8` 的 `sample_en`、`wave_fetch`、`voice_fetch` 预取触发、几百个寄存器的使能端。

**症状**：`.tr` 里最差的 25 条路径**全部**从 `cyc_5` 出发，终点分散在 `u_vf` / `u_fx` / `u_parse`。

**修法**：组合解码只驱动 2 个寄存器，寄存后的信号再送去扇出。

```verilog
reg [SW-1:0] slot_c;
reg          slot_vld_c;
always @(*) begin ... slot_c / slot_vld_c = 解码结果 ... end   // 只驱动 2 个 reg
always @(posedge clk ...) begin slot <= slot_c; slot_vld <= slot_vld_c; end
```

**副作用**：整体晚 1 拍。帧内 1024 拍，浪费 1 拍无影响；
两个 `voice_slot_seq` 实例由同一个 `frame_stb` 复位，延迟相同 → 仍然同步。

**判断"晚一拍是否安全"的方法**：看下游只依赖"顺序"还是"绝对时刻"。
`chan_layer` 的 `slot_cnt` 由 `frame_stb` 复位、`slot_vld` 递增 —— **相对关系不变** ✓

## 五、通用检查清单

**看到违例时，按这个顺序查：**

**① 先看 `Max Frequency Summary`**
所有违例在哪个时钟域？裕量差多少？

**② 看最差 25 条路径的 `From` 是否集中**
集中 → 一个锥，改一处就够
分散 → 可能是控制信号扇出，或者真的要改很多处

**③ 检查这几个常见元凶**

```
□ 一拍内两次乘法串联（乘法器延迟 3~5 ns，两次就吃掉大半周期）
□ 一拍内 "乘法 + 查表 + 再乘法"（查表是 mux，64 选 1 就有 5~8 ns）
□ 组合解码的计数/比较结果直接扇出到很多使能端
□ 常量被换成了运行时寄存器（常量折叠消失）
□ 64 位宽运算（比较器、加法器都很慢）
```

**④ 判断能不能拆流水**

```
这个运算每样本/每时隙只做一次吗？
  → 是：有几百拍可用，放心拆，代价只是延迟几个时钟
  → 否（每拍都做）：不能拆，只能改结构

拆流水有没有"位精确"的测试兜底？
  → 有：可以放心改，改错了测试会报
  → 没有：先补测试
```

## 六、几个容易踩的坑

### 6.1 综合与仿真对位宽的处理不同

**同一个表达式，iverilog 和 Gowin 可能算出不同位宽。**

```verilog
reg [31:0] interp;
interp = (r1 - r0) * {8'd0, dsemi[7:0]};           // 表达式在 16 位下求值！
interp = {16'd0, (r1-r0)} * {8'd0, dsemi[7:0]};    // 正确：操作数先扩到 32 位
```

**`iverilog` 会按 32 位算（所以测试通过），Gowin 按 16 位（所以上板出错）。**

**判断方法：看综合日志的 `EX3791 Expression size N truncated to fit in target size M`。**
**每一行都要对照自己本次修改的代码看。**

**这条规则要记牢：赋值语句左边不参与右边表达式的求值。要宽结果，必须把操作数本身变宽。**

### 6.2 `generate for` 里的模块级 reg 会多驱动

```verilog
reg [63:0] inc64;                       // 模块级
generate for (gi...) begin
    always @(posedge clk) inc64 = ...;  // 展开后 8 个副本都驱动它
end endgenerate
```

**iverilog 容忍（最后一次赋值生效），Gowin 报 `EX2000 Net 'inc64[47]' is constantly driven from multiple places`。**

**修法：用函数的局部变量。**

### 6.3 综合器会重排寄存器（流水可能被"优化掉"）

**给 SVF 加了 4 级流水，但网表里只有 2 级** —— 综合器做了时序优化，把相邻寄存器合并了。

**验证方法**：查 `.vg` 网表里的寄存器数量。
```powershell
# 统计某个模块里的 DFF 原语
$seg = $lines[$start..$end]
@($seg | Where-Object { $_ -match '^\s*DFF' }).Count
```

**如果加了几百位寄存器但网表里没有，说明被合并了** —— 需要换思路（比如关掉优化选项、或改变结构）。

### 6.4 Gowin 不会因为违例中止 P&R

**即使 1804 个违例，它照样生成 `.fs` 位流。**

**所以"综合+PR 成功"不等于"位流可用"。必须在烧录前看 `.tr`。**

## 七、操作流程建议

```
1. 改代码
2. 综合（5~10 分钟）
   → 看 EX3791 有没有新增行号（位宽问题）
   → 看 EX2000/EX1999（多驱动）
3. P&R 启动后 15 分钟看一次日志
   → 用"布局耗时"或"Phase0/1 耗时 × 2.5"估算总时长
   → 预估 >60 分钟 → 说明时序压力大，提前做好心理准备（或中断）
4. P&R 完成
   → 看 Numbers of Setup Violated Endpoints
   → 看 Max Frequency Summary 的 Actual Fmax
   → 看最差路径的 From / To
5. 判据（经验值）
   ≤300 违例、最差 slack > −1.5 ns   → 可以烧，先测功能
   300~600                            → 可以烧，留意偶发噪声
   >600 或 Fmax 明显低于要求           → 别烧，先修
6. 烧录后优先验证"功能有没有修好"，再谈时序
```

## 十、另一类时序问题：**模块之间的接口错位**

> 前面九节讲的是"单条路径太长"，这一节讲**完全不同的一类**：
> 逻辑本身没错、时序也收敛，但**两个模块对"什么时候数据有效"的理解不一致**。

### 10.1 症状

**实板单音演奏，声音像噪音/乱码，但上电的自检音（测试模式）完全正常。**

这个组合极具指向性：测试模式走 `test_voice_gen`，**不经过 DDS/SVF/ADSR/波表取数**，
所以问题一定在那条链上，而不是 DAC/功放/时钟。

### 10.2 Bug ①：扫描周期大于时隙间隔

```
wave_fetch  : 每个时隙要串行扫 2 × P = 16 个地址（全片只有一份波表 ROM）
voice_slot_seq : STRIDE = 32  →  时隙每 8 拍来一次
```

**16 > 8 → 扫描指针每 8 拍就被新的 `sample_en` 清零，永远扫不满。**

**实测数据（关键证据）**：

```
每帧 slot_vld = 4 次，rom_rdy = 1 次        ← 出错
每帧 slot_vld = 4 次，rom_rdy = 4 次        ← 修复后
```

**只有本帧最后一个时隙之后（不再有新时隙打断）扫描才能完成，**
**所以每帧只出 1 次波表数据，其余 3 个时隙的 `wave_out` 停在旧值**
**→ 输出变成阶梯状的低频噪音。**

**修法**：`STRIDE` 8 → 32。时隙在 1/33/65/97，扫描 17 拍完成，余量 15 拍。

> **教训**：串行资源（单口 ROM、单乘法器、单累加器）的**占用周期**必须小于**调度间隔**。
> 这个约束在代码里看不见，只能靠"数周期"来核对。
> **建议**：凡是"每个时隙/每帧串行处理 N 个东西"的模块，都要在注释里写明需要多少拍，
> 并在顶层参数处核对 `STRIDE` 是否够。

### 10.3 Bug ②：采样时刻早了 23 拍

```verilog
// chan_buf.v（错的）
end else if (slot_vld) begin        // 时隙起点就采样
    vmem[widx] <= {ch_in, aud_in};  // 但音频 23 拍后才有效
end
```

**实际的音频延迟链**：

```
cyc T      slot_vld
cyc T+2    波表扫描开始
cyc T+19   rdy → wave_out 更新
cyc T+23   SVF 4 级流水走完 → VCA 输出有效
```

**所以 `chan_buf` 存的是"上一个时隙的音频"，却配上了"本时隙的通道号和门控"**
**→ 声部与通道完全错位 → 噪音。**

**修法**：让"数据有效"这件事由数据源头自己声明的，而不是由下游猜：

```
① voice_mono 增加输出 data_vld = 内部的 vca_en
② full_system 把各泳道的 data_vld 取或，作为 ext_data_vld 传给 full_top
③ full_top 的 chan_layer 改成 .slot_vld(test_mode ? slot_vld : ext_data_vld)
```

**好处：不依赖硬编码的延迟拍数**，以后改流水级数、改 `STRIDE` 都自动对齐。

> **教训**：**跨模块的"数据有效"必须用专门的握手信号，不能用"节拍信号"凑。**
> `slot_vld` 表示"时隙开始"，不表示"数据就绪" —— 这两件事差了 23 拍。

### 10.4 为什么单元测试全过却漏了

```
tb_voice_mono     → 直接喂 tab_n / tab_n1，绕过了 wave_fetch     ← 盲区 1
tb_chan_layer     → 直接喂 aud_in，绕过了 voice_mono             ← 盲区 2
tb_bend_glissando → 只看 pf_phase_inc，没检查音频波形             ← 盲区 3
```

**三个测试台都在"接口边界"上做了替身，所以边界本身的时序没人验证。**

**建议补的测试**：

```
① 每个时隙的 rom_rdy 是否都拉高（数一帧里的次数）
② 单音的 sample_l 是否是指望的频率（数过零）
③ chan_buf 里存的音频是否对得上它的通道号
```

### 10.5 一个通用检查清单

**看到"声音是噪音/乱码"时，按这个顺序查：**

```
□ 是不是有"节拍信号"被当成了"数据有效信号"？
□ 串行资源的处理周期是否小于调度间隔？
□ 数据从产生到被消费，中间隔了几拍？下游知道吗？
□ 先确认"自检音/测试模式"是否正常 —— 正常就说明问题在特定模块链上，
  不在时钟/DAC/功放
```
